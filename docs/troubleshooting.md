# Troubleshooting

[Back to the README](../README.md)

`omarchy-anime` in a command here is the plugin's own command, on your PATH once you have run the link line in
the README's [Install](../README.md#install).

Every click carries a trace id through the whole pipeline. To see what happened:

```sh
omarchy-anime trace last
```

That prints, as a timeline, the newest thing you started yourself: a play (from the overlay, the popout, a keybind,
the player's episode list or auto-next), a resolve, a sign-in or sign-out, a change in Accounts, a progress write
to AniList, a player start or restart, a new search in the release list (`r`, or your own words), a subtitle fetch.
For a play the timeline holds the title lookup, episode mapping, release search, scoring, the provider, mpv,
subtitle selection, and the Hyprland window. It passes over what the plugin runs by itself (the status poll, list,
detail and account reads, cover downloads, the progress retry, the release list a refused play opens), the bar's
window and play/pause buttons, and commands that only read (`accounts`, `torbox-user`, `status`, `watching`…), so
you can run those first; when it passed over newer traces, its first line says how many, and what they were.
The release list is passed over even when it has to search again (its stored search is over 30 minutes old, or the
episode was never searched): a failed search there shows its error in the list itself.
`trace <id>` renders a specific one —
`t` in the overlay copies the id of the last failure to the clipboard. The raw lines are JSON in
`~/.cache/omaanime/log/<date>.jsonl` (kept for 14 days), and the `version` in the `cli start`
line is the plugin version, which is what to quote in a bug report.

| Symptom | Where to look |
|---|---|
| "Nothing plays" | `omarchy-anime torbox-user` — an expired plan answers here first, and says *plan*, not *token*: TorBox's `/user/me` keeps answering 200 after a trial ends and only the streaming calls turn 403. Then `omarchy-anime trace last`. When the command failed, its closing `failure:` line names the stage that ended it, with its error and what to do. When no failure was logged, an `unrecovered:` line may name the last step that failed and was not retried into a pass: a lead to read, not a failed command. |
| "No indexer is set up", or an add-on or server you added is missing | Settings in the Anime bar popout (or `omarchy-shell omaanime browse settings`) lists the add-ons that loaded (`torznab` with its server and feed counts) and, for each file that did not, why (see [Indexer add-ons](addons.md#indexer-add-ons)); **Check** on a server in Accounts says what is wrong with it, and `omarchy-anime addons check <file>` what is wrong with an add-on file and what its search answers. `omarchy-anime accounts` prints the same list, and the last play's timeline (`omarchy-anime trace last`) has an `indexers` line per add-on call. |
| "No <your language> subtitles" on every release | Some sources simply have none — whether a language is there is decided by the streaming platform's licence, not by the release group, so when the streaming platform ships no track in your language for a title, no release of it has one. `subtitlePolicy: "prefer"` plays the best release anyway and says so in the popout; among the releases, one with your second language (`subtitleFallbackLanguage`, English by default) ranks higher. |
| The popout says "added from […]" | The release being played had no track in your language, so the plugin borrowed one from another release of the same episode and loaded it as an external file. The line names the donor. `omarchy-anime subs find <mediaId> <episode>` lists every candidate from the terminal. |
| The borrowed subtitles are out of sync | The popout says which case you are in. "same … source" or "shifted +N s" means the timing was checked against both releases' English tracks; "timing unverified" means no shared language existed to check against and the file was loaded as-is. Either way the popout has ⏪ / ⏩ buttons under the subtitle line that move the whole track a second at a time (↺ undoes them), and `omarchy-anime player sub-delay +1.5 | --set S | --reset` does the same from a terminal. mpv's own `z` / `Z` still work inside the player window at 0.1 s a press, and `Ctrl+Shift+Left/Right` snap to the previous or next line. The delay is reset on every new episode. Set `subtitleSyncMaxOffset` to 0 to stop the plugin shifting anything. |
| No release has your language at all | Add a free **Subdl** key and/or an **OpenSubtitles** API key in Accounts. The play then looks for your language in both databases while the episode starts (also when a borrowed track's timing could not be checked), and adds the three best files that name this show and episode as subtitle tracks, a few seconds in. `j` in the player cycles them; each track title says where it came from and whether its timing was checked. Accounts shows how many searches (Subdl) or downloads (OpenSubtitles, 100 a day) are left today. `omarchy-anime subs external <anilist id> <episode>` lists what would load; add `--release-id <indexer> <release id>` to ask with that release's show ids too, when its indexer add-on offers them (otherwise ani.zip's alone are used). |
| Borrowed subtitles are in the wrong language, or you want them off | `omarchy bar set io.github.asemhub.omaanime sideloadSubtitles false --json`. |
| The subtitle cache is growing | `omarchy-anime subs status` shows what is there and `omarchy-anime subs prune` empties what has not been used for 30 days and cuts the rest to `subsCacheMaxBytes` (16 MiB). It prunes itself once a day, after a play, anyway, and the files are 20-30 KB each. |
| The picture cache is growing | `omarchy-anime thumbs status` shows the derived pictures (player-row buffers, blurred stills, fanart, logo) and their sizes; `omarchy-anime thumbs prune` empties what is stale or over the limit now. It runs itself once a day, after a play, same as the subtitle cache. |
| Continue Watching or the Lists tab says "AniList isn't answering right now." or "Can't reach AniList right now.", then "This is your list from …" | AniList is down (the first), or can't be reached from here, which may be your own network (the second). The plugin shows the list it saved the last time AniList answered, and says when that was. Progress you watch meanwhile is queued and sent when AniList is back. The plugin asks AniList again every 5 minutes, and the line goes away on the first answer. A sign-in AniList refuses still asks you to sign in again, with no rows. A sign-in that has expired shows the saved rows and the line during an outage, with the notice "Your AniList token has expired. Sign in again…" beside them. |
| Browse's Top 100 or Airing tab says "AniList isn't answering right now. This is Top 100 from …" (or "This is Airing from …") | The same outage: the tab shows the copy it saved the last time AniList answered, however old, and says when that was. It asks AniList again each time you open the tab (or press `r`), and the line goes away on the first answer. On Airing, an episode whose time has passed since that copy reads "Ep 7 aired": the copy cannot say what came after it. |
| "Player stopped answering; restarting it" | mpv's video thread can hang on some hardware; the plugin kills and replaces the player once every 30 seconds until it answers again. If it repeats, `omarchy-anime player start` by hand. |
| An episode takes a long time to start | Watch the line at the bottom left of the video: it names the provider being asked and counts the seconds. A provider that refuses three releases in a row is dropped for the rest of that play and for the next 15 minutes, and the line says so — *"Real-Debrid isn't answering for this episode, so trying TorBox instead."* `omarchy-anime accounts` says whether either token is still good, and `omarchy-anime trace last` shows the `provider.block` line with what the refusals cost. If a provider you have just paid for is being skipped, wait for the 15 minutes (`providerBlockMinutes`) or run one play — it re-probes once and clears itself on the first success. |
| A play failed and the message is a string of stage names | It is not one any more. The first sentence names the cause and the one thing that fixes it — *"Real-Debrid refused the account for every release tried."*, then what to check in Accounts — and the same sentence is what the popout, the bar panel and the line at the bottom of the video all lead with. The per-provider detail is still there behind it, and `omarchy-anime trace last` has all of it. |
| An episode you clicked seems to have restarted itself | It no longer can. While a play started from the overlay, the popout, a keybind or `omarchy-shell omaanime play` is still starting, another one asked for from any of them is not started: the overlay and the popout say "Episode N is already starting." (the same episode) or "Not started: episode N is still starting." (another), and the IPC answers `refused: …` instead of a trace id. Ask again once it plays. In the player's episode panel, a second click on the episode that is already starting says "is already starting" and changes nothing; a click on a *different* episode says "Switching to episode N" and stops the first attempt before starting the second. One exception: while the starting play is waiting for TorBox to download the episode (which can take hours), another episode, or a release you pick for the same one, goes ahead and ends that wait (the download carries on in TorBox). If you see an episode restart, `omarchy-anime trace last` and the `play.claim` line say which process did it. |
| A play failed and you missed the message | It is still in `~/.cache/omaanime/play-status.json` — `state`, `failedStage`, `error` and `suggest` — until the next play replaces it, and `omarchy-anime trace <its trace>` renders the whole attempt. |
| A change to the in-player episode panel does nothing (clicks, the ☰, the wheel) | The player process predates the change: see the "has been running since before" row below. `omarchy-anime player restart`. |
| The overlay or the bar does not show a change you made | Panel, overlay and service QML are not hot-reloaded: `omarchy restart shell`. |
| The player window is cut off at an edge, or is the wrong size | The plugin sizes it to 90 % of the monitor it is on (largest 16:9 box inside the usable logical area) every time it parks, and re-fits it whenever it no longer fits. `omarchy-anime player start` re-parks it now; `omarchy-anime trace last` shows the `hypr/park` line with `usable`, `wanted` and `applied`. If something else in your Hyprland config floats or sizes this window, that rule wins — the plugin needs no such rule. |
| "AniList is nearly rate-limited" | AniList allows 30 requests a minute. The plugin paces itself at 80 %, warns at 90 % and refuses at 100 %; it recovers by itself within the minute. |
| "Your AniList token expires in N days" | `omarchy-anime auth anilist` again, or **Replace** on the AniList row in Settings. The token lasts a year and cannot be refreshed. |
| "I want to disconnect a provider" | `omarchy-anime signout <anilist\|torbox\|realdebrid\|subdl\|opensubtitles>`, or **Sign out** on its row. It removes the token file and what the account left behind ([the list](privacy.md#what-is-stored-and-where)). Running it twice is not an error. |
| Progress did not reach AniList | Failed writes are queued in `~/.cache/omaanime/pending-progress.json` and retried at every launch and every ten minutes. `omarchy-anime flush-progress` forces it. Each is sent only to the AniList account it was queued under. |
| The popout says "The player has been running since before … changed" | mpv reads its Lua script **once, at process start**, so a player that was already running when the plugin updated keeps using the copy it loaded — the episode panel opens but the newer parts of it quietly do nothing. `omarchy-anime player restart` replaces the process and re-loads the episode where you were; `omarchy-anime player stop` cannot fix it, because it stops playback and leaves the same process running. |
| The popout says "Lost the live player connection" | The plugin's IPC socket to mpv is down while mpv is still playing. It rebuilds the socket every second, then every two, four… up to fifteen, and it keeps tracking your progress in the meantime from its own 10-second status poll — so the resume position and the AniList write still happen, at 10-second resolution instead of 5. **One thing does not survive it: autoplay-the-next-episode**, which fires on an mpv event only the socket can see. The notice clears itself when the socket comes back; if it never does, `omarchy restart shell`. |
